# Capability: Generate SQL

## What It Does
Calls the LLM to generate a single, safe `SELECT` statement from the user's question, the analysis plan, and the data schema — then sanitises the output before returning it to the execute step. Retries up to 3 total attempts when SQL execution fails.

## Inputs

| Input | Type | Source | Required |
|-------|------|--------|----------|
| `question` | `str` | User's question | Yes |
| `schema_text` | `str` | `ingest_csv_node` output | Yes |
| `plan_text` | `str` | `plan_node` output | Yes |
| `sql_error` | `str \| None` | Error text from `execute_query_node` (retry feedback loop) | No |
| `sql_attempts` | `int` | Counter incremented per call to this node | Yes |
| `AGENT_SQL_MAX_ATTEMPTS` | `int` | Env var (default 3) | No |

## Outputs

| Output | Type | Destination |
|--------|------|-------------|
| `sql_text` | `str` | `AgentState` — consumed by `execute_query_node` |
| `sql_attempts` | `int` | `AgentState` — incremented per call |
| `error` | `str \| None` | `AgentState` — set when `sql_attempts >= AGENT_SQL_MAX_ATTEMPTS`, routes to `handle_error_node` |

## External Calls

| System | Operation | On Failure |
|--------|-----------|------------|
| Ollama HTTP `POST /api/chat` | Generate SQL | Retried by the LLM client retry decorator (max 2 HTTP-level retries). After HTTP retries exhausted: node catches `LLMError`, sets `state["error"]`, routes to `handle_error_node`. |

## Business Rules

- **One SELECT only:** The LLM is instructed to return exactly one `SELECT` statement. The node's post-processing strips markdown fences (`` ```sql ... ``` ``) and extracts the first statement beginning with `SELECT` (case-insensitive). If no SELECT is found after stripping, the node treats it as a generation failure.
- **No DDL / DML:** If the extracted SQL contains `INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `CREATE`, `EXEC`, or `EXECUTE` (case-insensitive), the node sets `state["error"] = "Only SELECT queries are permitted"` and routes immediately to `handle_error_node` — no retry. This is a hard safety constraint.
- **Retry feedback:** When `sql_error` is non-None (coming from `execute_query_node`), the user message appended to the LLM call is: `"PREVIOUS SQL FAILED WITH ERROR:\n{sql_error}\n\nReturn a corrected SELECT statement only."` (truncated to 500 chars of the error). The LLM is told not to include explanations or markdown in the SQL output.
- **Max attempts:** `sql_attempts` is incremented at the top of the node before the LLM call. If `sql_attempts >= AGENT_SQL_MAX_ATTEMPTS` (default 3), the node sets `state["error"]` instead of calling the LLM, causing the conditional edge to route to `handle_error_node`. This prevents an infinite retry loop.
- **SQL is never user-interpolated:** The SQL text is generated entirely by the LLM; it is never combined with user input values via Python string formatting (all user-provided numeric/text filtering must happen at the SQL literal level generated by the LLM, not by Python-side interpolation).

## Success Criteria

- [ ] For question "How many records?" the first SQL generated is `SELECT COUNT(*) AS count FROM data;` (or equivalent)
- [ ] When `sql_error = "no such column: foo"` is injected (simulated in test), the retry SQL references only columns from `schema_text`
- [ ] After 3 failed SQL attempts (simulated by injecting `sql_error` that causes repeated failures), `state["status"]` is `"failed"` and `error` contains "SQL generation failed after 3 attempts"
- [ ] A SQL generation returning markdown fences (`` ```SELECT ... ``` ``) is correctly unwrapped to the bare SQL statement
- [ ] A SQL generation containing `DROP TABLE` is rejected immediately with `error = "Only SELECT queries are permitted"` and no retry is attempted
